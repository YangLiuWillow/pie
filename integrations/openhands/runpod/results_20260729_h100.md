# H100 re-baseline — measurements, 2026-07-29

`predictions/` and `logs/` are gitignored and pod-local. Every number here names
the file it came from so it survives the pod.

**Board:** NVIDIA H100 80GB HBM3, sm_90, 132 SMs, driver 580.126.09, CUDA 13.0.
**Not an H200.** The 2026-07-28/29 series ran on H200 141GB; absolute values here
are lower by roughly the HBM3-vs-HBM3e bandwidth ratio and are not comparable.
Ratios *between arms on this board* are the quotable thing.

**Versions:** vLLM 0.25.1, torch 2.11.0+cu130, Triton 3.6.0, openhands-sdk 1.21.1
= openhands-tools 1.21.1, litellm 1.84.0, harness deps `--exclude-newer 2026-05-15`.

## 2. MoE config for the `fair` tier — chosen by measurement

vLLM ships no config for this device. Two candidates, 2 replicates, agreement
~0.5% (`logs/moe_bench_*_20260729_1759*.log`, `12_validate_moe_config.sh`):

| regime | SGLang H100 (device-name-correct) | vLLM H200 config |
|---|---|---|
| decode bs 1-8 | **+0.3% (slower than vLLM's default)** | **-2.9%** |
| mid bs 16-512 | +1.5% | +0.1% |
| prefill bs >=1024 | -4.1% | -3.7% |
| overall | -1.2% | **-1.9%** |

**Chosen: vLLM's H200 config**, installed under the H100 device name. The
device-name-correct SGLang config loses to vLLM's own default in decode, likely
because it lives in SGLang's `triton_3_2_0/` and we run Triton 3.6.0. Candidates
preserved at `/workspace/moe_candidates/`; provenance and full tables in
`/workspace/tuned_moe_h100/{PROVENANCE,VALIDATION}.md`.

**Finding:** the tuned-MoE lever is worth **~1.9% on H100** against **-8.3% on
A100**. "The baseline was crippled by an untuned MoE kernel" is a much weaker
effect on this board; `--enforce-eager` remains the larger term.

## 4. Stage profile — where the gap actually was

`42_context_sweep.sh` with `SWEEP_MODE="prefill context"`,
`logs/ctxsweep_20260729_185619/`. Both modes use the differencing method: hold one
axis fixed, vary the other, so per-call overhead cancels and the two client stacks
become comparable.

| stage | pie | vLLM | ratio |
|---|---|---|---|
| decode intercept (weights/MoE/router/launch) | 5.219 ms/tok | 4.686 | 1.11x |
| decode slope (KV read) | 0.0329 ms/kKV | 0.0348 | **0.95x — pie wins** |
| -> implied KV bandwidth | **2,988 GB/s (89% of peak)** | 2,829 (84%) | pie 1.06x |
| decode total @25k ctx | 6.04 ms/tok | 5.56 | **1.09x** |
| **prefill** | **5,169 tok/s** | **44,855** | **8.6x** |
| fixed per-call | 147.6 ms (corrected) | 129.6 | 1.14x |

**Decode is at parity** — the H200 result (1.06x) reproduces here at 1.09x, and
Pie's decode *attention* now beats FlashAttention-3 on the same GPU. **Prefill was
the whole gap**, accounting for ~72% of the closable difference.

Two caveats on the prefill measurement: all 15 pie samples reported
`mode=rebuilt`, so the sweep never exercised Pie's incremental path — the SLOPE is
still valid and comparable (the constant base cancels) but the raw intercept
needed a base-prefill correction. And vLLM's prefill fit R2 was 0.914 vs pie's
0.988, so 8.6x is good to one significant figure only.

## 5. The fix — on-device MoE for prefill

`qwen3_5_moe_forward.cpp`: `PIE_QWEN35_MOE_DECODE_FAST_N` ceiling raised 128 ->
8192, default flipped to always-on-device.

Root cause: the prefill branch of `moe_block()` was host-orchestrated — per LAYER
one D2H copy of the routing table plus one **full `cudaStreamSynchronize`**, then a
128-iteration expert loop each with 2 H2D copies, 3 kernels and 2 cuBLAS GEMMs of
M ~= N*K/E. Over 48 layers: ~43,000 GPU ops and 48 pipeline stalls per forward,
independent of token count. The on-device path (device-built route/pointer arrays,
2 `cublasGemmBatchedEx` per layer) already existed but was capped at 64 tokens
while agent prefill chunks are ~1,000.

A/B, same binary, same server config, only the flag differs
(`logs/ctxsweep_20260729_192052` vs `_192819`):

| | host (64) | on-device (512) | gain |
|---|---|---|---|
| prefill marginal | 5,183 tok/s | **12,058** | **2.33x** |
| prefill, measured at 5 sizes | — | — | **2.61x - 2.74x, mean 2.69x** |
| real agent instances | 2,917 / 3,088 | **8,364 / 9,260** | **2.87x / 3.00x** |
| **decode CONTROL** (must not move) | icept 5.113 / slope 0.03427 | 5.184 / 0.03418 | **+1.4% / -0.3%** |

The decode control matters: `is_pure_decode` already selected this path regardless
of the flag, so movement there would mean the flag was doing something other than
advertised.

Correctness: both verification instances produced the **canonical upstream fixes**
(`use_required_attribute` moved to `FileInput`; `'%04d' % year`), zero errors, zero
stuck retries, zero non-ASCII bytes in the patches.

Gap to vLLM on prefill: **8.6x -> 3.6x**.

## 6. Levers that did NOT work — recorded so they are not retried

**Aligned block size** (`PIE_QWEN35_MOE_ALIGNED_DECODE_BLOCK`), prefill tok/s
(`logs/ctxsweep_20260729_{200405,201000,201217}`):

| block | prefill tok/s | vs 16 |
|---|---|---|
| 16 (default) | 12,046 | — |
| 32 | 12,487 | +3.7% |
| 64 | 11,817 | -1.9% |

`aligned_rows` uses a **worst-case bound at runtime** —
`(routes + E*(block-1))/block*block` regardless of actual routing — so block=16
already wastes 47%, and 32/64 cost 1.34x/2.02x more issued FLOPs. 32's tile gain
just clears its padding penalty; 64's does not. **A ~4% effect; not a lever.**

**Aligned MoE path for single-stream decode — CLOSED, it is 13.4% WORSE.**
At c1 the decode path has `routes = N*K = 8`, below
`PIE_QWEN35_MOE_ALIGNED_DECODE_MIN_ROUTES` (default 64), so it takes the
NON-aligned path: 8 batched GEMVs of M=1 per layer, 384 per forward. The
motivating asymmetry was large: the decode intercept reads 5.06 GB of weights per
token at **0.97 TB/s = 29% of HBM peak**, while decode ATTENTION reads KV at
**2,988 GB/s = 89%** — two memory-bound operations on the same GPU, 3.1x apart.

Lowering the threshold routes c1 decode through the aligned path (M=block=16). It
pads 8 routes to 128 rows, but the same 8 experts are read either way, so weight
traffic is unchanged and only the GEMM shape differs — which looked like a free
win on a weight-bandwidth-bound path.

Measured (`logs/ctxsweep_20260729_{223539,224144}`):

| | MIN_ROUTES=64 | MIN_ROUTES=8 | delta |
|---|---|---|---|
| decode intercept | 5.214 ms/tok | **5.914** | **+13.4% WORSE** |
| decode slope | 0.03261 | 0.03241 | -0.6% (flat) |
| implied KV read | 3,014 GB/s | 3,033 GB/s | flat |
| prefill (CONTROL) | 12,153 tok/s | 11,890 | -2.2% (within the +-3% band) |

Baseline reproducibility: intercept 5.214 here vs 5.219 measured hours earlier,
**0.1% apart**, so the regression is real.

**What this establishes matters more than the failed hypothesis: the 29%-of-peak
weight read is NOT a GEMV-shape artifact.** A taller M did not help, so the
deficit is the SCATTER — 8 non-contiguous experts' tensors per token, against
attention's contiguous KV pages. That is structural to MoE decode at batch 1, and
the 3.1x was a ceiling rather than headroom. The 16x row padding costs more than
the shape change gains.

**Default stays at 64. The decode-intercept lever is closed**, alongside MoE
kernel selection (AGENT_HANDOVER_20260728.md 6a-bis).

**CUTLASS fused MoE with SwiGLU — BLOCKED ON A BUILD, not a capability.**
Three successive diagnoses of this were wrong; the final one is:

**The Hopper TMA warp-specialized MoE GEMM launchers are not compiled into our
FlashInfer build.** The gate is `#ifndef COMPILE_HOPPER_TMA_GROUPED_GEMMS`
(moe_gemm_template_dispatch_tma_ws.h:136). Defining it is NOT a one-line change:
the dispatch then references per-tile/cluster launcher instantiations that
upstream GENERATES (`build_wheel.py --arch 90-real`), and the vendored tree ships
only the template (`moe_gemm/launchers/moe_gemm_tma_ws_launcher.inl`) with zero
`.cu` files instantiating it. Enabling the define fails at link with hundreds of
undefined `tma_warp_specialized_generic_moe_gemm_kernelLauncher<Sm90, ...>`
symbols. Making it work means generating those TUs, absorbing a large compile,
and accepting that it also widens the tactic set Nemotron-H selects from.

**The failure mode is dangerous and worth knowing.** It is a TLLM_THROW at
DISPATCH time, after the model is loaded — not at workspace-query time. So
"probe the workspace size first" does NOT protect you: getWorkspaceSize returns a
confident 40 MiB for a shape whose kernel does not exist, and the dispatch then
kills the driver ("driver did not emit capabilities within 600.0s", zero rows).
`flashinfer_cutlass_moe_swiglu_enabled()` was therefore made to return false
unconditionally without the define, and the doctor probe now prints a banner
saying its `OK` rows mean "shape is describable", not "kernel exists".

**Two real API traps found along the way, both still true and worth recording:**
 1. `getWorkspaceSize`'s third parameter is `fc1_output_size` (= 2*inter_size for
    a gated activation), while `runMoe` takes `inter_size` in the corresponding
    slot. The two calls want DIFFERENT values from one shape. Passing inter_size
    to both is right for Relu2 and silently wrong for SwiGLU.
 2. The runner is order-dependent: `getMaxWorkspaceSize` caches on `num_experts_`
    and a COLD first call can report "Could not find valid config" for a shape it
    serves on the next call. The probe demonstrates this by repeating one row.

Neither trap was the blocker, but both would bite anyone retrying this.

**The lower-level `MoeGemmRunner` split route is NOT a way around this** — it
depends on the same uncompiled TMA-WS launchers.

The integration was written, fixed, and then **reverted**; only the shape probe
was kept.

## 7. What is left, and what is NOT true

**Prefill remains the ONLY open lever** (~8,610 tok/s on the real workload vs
vLLM's 44,855, i.e. ~5.2x) and it needs the TU-generation build project above.
Decode is finished: Pie's attention already beats FA3 here (slope 0.0329 vs
0.0348), the intercept gap is 1.11x, and both ways of attacking that intercept --
MoE kernel selection (6a-bis) and the aligned decode path (this document) -- are
now measured closed.

**Paired c1 result, both vLLM samples same-board same-config:**

| arm | s/iter | p50 | in-call tok/s |
|---|---|---|---|
| pie, on-device MoE | 1.204 | 1.058 s | 144.4 |
| vLLM fair #1 (18:36) | 1.042 | 0.829 s | 161.7 |
| vLLM fair #2 (22:14) | 1.080 | 0.860 s | 159.1 |

vLLM reproduces to **1.6%** on in-call throughput (3.6% s/iter, 3.7% p50), so the
single-sample caveat does NOT apply at c1 -- 10e's ~50% swing was a c8 phenomenon.
Gap against the mean of two: **in-call 1.11x, s/iter 1.14x, p50 1.25x.**

p50 lagging throughput (1.25x vs 1.11x) says the residual disadvantage is
concentrated in per-call fixed cost (147.6 vs 129.6 ms), not streaming rate.

**c1 is likely Pie's WORST case.** On H200 Pie gained on vLLM as concurrency rose
(1.39x -> 1.21x from c8 to c16, vLLM saturating while Pie did not). This board
cannot test that honestly at 1.03x KV headroom, so the concurrency question is
open, not answered.

**It is NOT true that Pie's architecture caps it below vLLM.** An earlier note in
this investigation claimed the needed capability — a grouped GEMM taking
per-expert sizes from device memory — was unique to Triton. It is not:
`cutlass/gemm/group_array_problem_shape.hpp` holds `problem_shapes` as a **device
pointer** and treats `host_problem_shapes` as **optional**, and
`MoeGemmRunner<bf16,bf16,bf16>` is already explicitly instantiated in this build.
Triton's advantage is convenience (Python JIT + autotuning), not capability.

**Concrete untried route:** two **non-gated** grouped GEMMs via the lower-level
`MoeGemmRunner` with an elementwise SwiGLU between them, sidestepping the gated
minimum that the probe identified — non-gated is confirmed working at inter=768.
Probe it before building it.

## 8. Method notes worth keeping

- **`inst/hr` is the most trajectory-contaminated metric here and should not be
  the headline.** Prefer in-call tok/s and s/iter; report aggregate tok/s only for
  concurrent arms where system throughput is the question.
- **Three code readings were wrong today**, each corrected by a measurement that
  cost minutes: that `block=32` would be free (the worst-case padding formula says
  otherwise); that being in the activation dispatch switch meant SwiGLU would work
  (the config search says otherwise); that device-side grouped GEMM was
  Triton-only (CUTLASS has it). The standing rule holds: **prefer a number over a
  reading**, and when a cheap probe is available, run it before writing code.
- **c8/c16 arms were NOT re-run on this board.** With ~1.03x concurrency headroom
  they would run under KV pressure the H200 arms never saw, so the H200 1.39x at
  c8 is not comparable and was not reproduced here.
