1. THE HEADLINE FINDING -- THE A100 PIE ARM IS NOT A VALID PIE MEASUREMENT
================================================================================

Pie's two fast attention paths are hard-gated to CUDA compute capability >= 9
(Hopper and newer). The A100 is sm_80, major 8. Both were OFF for the entire
Pie run, silently.

    driver/cuda/src/entry.cpp:988-989
        fwd_cfg.use_prefill_decode_plan =
            (serving_prop.major >= 9 || force_prefill_decode_plan) && ...

    driver/cuda/src/ops/attention_xqa.cu:274
        return current_device_major() >= 9;    // xqa_decode_bf16_supported

The driver printed this in its own startup banner and we read past it:

    [pie-driver-cuda] ... prefill_decode_plan=off xqa_decode=off decode_plan_graph=on

Device confirms the gates fail:
    name=NVIDIA A100-SXM4-80GB  major=8  minor=0  SMs=108
    serving_prop.major >= 9      -> False
    current_device_major() >= 9  -> False

PIE_CUDA_XQA_DECODE defaults to ON, so xqa is not disabled by choice -- the
SUPPORT CHECK fails on Ampere. PIE_CUDA_PREFILL_DECODE_PLAN=1 can force the
other path on, but that pushes a Hopper-gated kernel onto Ampere. Not a
validated configuration. Do not use it for a headline number.

1.2 WHY THIS EXPLAINS THE WHOLE EXPERIMENT
--------------------------------------------------------------------------------

build_pie_cuda.sh:7 confirms the ORIGINAL writeup targeted
RTX Pro 6000 Blackwell = sm_120 = major 12. Both >= 9 gates PASS there.
On this A100 both FAIL.

  - the original "+26% for Pie" was measured with Pie's fast paths ON
  - this rerun measured Pie with them OFF

The config-effort axis this rerun was built to test (--enforce-eager, tuned
MoE kernel) is NOT what moved the number. We spent the day auditing the wrong
variable.

DO NOT PUBLISH "vLLM is ~10x faster than Pie" FROM THIS DATA.
It measures Pie's fallback attention path. It is exactly as much a hardware
artifact as the claim it was meant to correct, just pointing the other way.
TEST_PLAN.md section 7 says audit for a confound before celebrating a Pie win.
The rule has to be symmetric. This is the confound.

A800 is the same GA100 silicon as A100: identical compute, 80 GB HBM2e,
~2 TB/s memory bandwidth. The ONLY difference is NVLink, 600 -> 400 GB/s. We
serve tp=1 on a single GPU, so NVLink is never touched by the fused MoE kernel.

Corroboration in the file itself: it caps num_stages at 2-4, whereas the
shipped H200 config uses num_stages=5 at bs=1. That is what sm_80 tuning looks
like -- 164 KB shared memory per SM will not hold as deep a pipeline as
Hopper's 228 KB.

Format compatibility is by lineage, not luck: vLLM's get_moe_configs carries
the comment "Adapted from: https://github.com/sgl-project/sglang/pull/2628",
the JSON schema is identical, and vLLM pops triton_version and ignores it.

6. OPEN DECISIONS (yours)
================================================================================

6.1 WHICH GPU
--------------------------------------------------------------------------------
A valid Pie comparison needs sm_90 or newer. Two candidates:

  H200 (sm_90, major 9)
    + Pie's two attention fast paths turn ON
    + vLLM SHIPS the tuned E=128,N=768 bf16 MoE config -- neither side needs
      tuning from us, strongest possible methods sentence
    + mainstream hardware, more representative for readers
    - NOT identical to the original writeup's Pie config (misses the >= 12
      wide-prefill settings)
    - requires rebuilding pie for sm_90 (CMAKE_CUDA_ARCHITECTURES=90;
      build_pie_cuda.sh:7 documents h200=90) and re-running the Pie arm

  RTX Pro 6000 Blackwell (sm_120, major 12)
    + EXACTLY reproduces the original writeup's Pie configuration, so it is the
      only venue where a null result actually refutes the original claim
    + build_pie_cuda.sh already defaults to sm_120
    - no shipped vLLM MoE config for this shape -> autotune or borrow again

  Choose by thesis:
    "we re-examined our own +26% claim"          -> sm_120 (RTX Pro 6000)
    "how Pie and vLLM compare on mainstream HW"  -> H200

  DO NOT use B200: sm_100 is new enough that Pie's own kernels may be immature
  there, which introduces a confound you cannot disentangle from architecture.
  GB200 and RTX Pro 6000 also lack a bf16 E=128,N=768 vLLM config.

  WATCH OUT if moving to H200/B200: the tuned MoE config SHIPS there, so
  'graphs-only' and 'crippled' (both defined as DEFAULT MoE) would need the
  shipped JSON physically moved aside. VLLM_TUNED_CONFIG_FOLDER only PREPENDS a
  search path, it cannot suppress the package file. Recommend dropping the
  'graphs-only' tier on those GPUs -- there, "what you get without the
  autotuner" means "what you get if you delete a file vLLM ships", which is not
  a configuration any real user is in.
