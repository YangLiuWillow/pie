Serving-system evaluation · LLM inference

Can Pie outperform vLLM + APC?

An honest, aggregated evaluation of the Pie serving system as a backend for two integrations — genetic code evolution (OpenEvolve) and agentic SWE-bench (OpenHands) — against vLLM with automatic prefix caching.

Model · Qwen3-Coder-30B-A3B GPU · RTX PRO 6000 Blackwell 96 GB Baseline · vLLM + APC 2026-07-21

0Bottom line

On a single local GPU with vLLM's automatic prefix caching enabled, Pie does not beat vLLM on wallclock for our workloads. Its best observed case is a tie; in the agentic setting it is up to 3.65× slower. The cause is structural — vLLM's APC captures the same KV reuse that Pie's fork/session provides, so Pie's headline mechanism is not a differentiator, and Pie then loses on secondary overheads.

Pie's mechanisms work — they eliminate 95–97 % of prefill in agentic loops and fork shared prefixes perfectly — but that saving does not convert to wallclock, because the baseline already gets the same reuse for free. The paper's real wins (1.3–3.4× on agentic workflows) are genuine but conditional: they need a small model + a real network gap + many I/O interactions + concurrency that makes APC evict + tools that run inside the inferlet. Our environment removes every one of those conditions.

1Why the two engines tie on reuse

vLLM's APC hashes KV-cache blocks by token content and reuses them across requests. A multi-turn agentic loop is, turn by turn, an append-only growing prefix:

turn 1:  [system + task]
turn 2:  [system + task + assistant_1 + tool_result_1]
turn 3:  [system + task + assistant_1 + tool_result_1 + assistant_2 + tool_result_2]

A growing prefix is exactly what APC reuses: on turn 3 it recognizes turns 1–2 as cached and prefills only the new tail — the same computational saving Pie's session gives. So "multi-turn / agentic" is not, by itself, a Pie advantage. Pie beats APC only when the app does something that is not a plain growing prefix (mid-context drop, mid-decode branching, custom attention) — or when the transport/round-trip around the reuse dominates (a network gap), or when the tool runs inside the inferlet (co-location).

2The integration variants we built

2.1 · OpenHands (agentic SWE-bench)

OpenHands drives an agent that reads a GitHub issue, explores the repo, edits source, runs the tests, and submits a patch — a long multi-turn loop with heavy tool use. We wired it to Pie four ways. What separates them is two design axes: where the agent loop runs (in a Python client, or inside the WASM inferlet), and how the KV context is carried between turns (re-established each call, or kept live).

Pattern B vs Pattern A is the load-bearing distinction. In Pattern B the Python loop calls a stateless inferlet once per turn; the inferlet re-opens the session's KV snapshot and refreshes it (a delete + save) on every call. In Pattern A the entire loop lives inside one long-running inferlet, so the KV context is created once and simply appended to — no per-call teardown. Experiments #02, #06, #11 show that per-call teardown was most of Pattern B's 3.65× deficit.

Anatomy of Pattern A openhands-agent

One Context is created, seeded with the system prompt + task, and then driven through a fixed step loop. Every step's action is grammar-constrained to a flat JSON schema (constrain_with(JsonSchema)), so the model must emit a valid action — {thought, action, command, path, old_str, new_str, …} — with action ∈ {bash, edit, read_file, insert, undo_edit, finish}:

  1. Condense if needed — before generating, if the effective context nears context_token_limit, either rebuild (summarize dropped turns + re-prefill) or mask (drop stale-middle KV out of attention, 0 re-prefill). A cooldown prevents condense-every-step.
  2. Generate the action — decode a grammar-constrained JSON step into the same live ctx (the last step is forced to a finish schema).
  3. Yield the GPU — ctx.idle() releases the KV pages while the tool runs, so a slow bash/test call doesn't hold GPU memory idle.
  4. Run the tool on the host — POST a ToolRequest over HTTP to tool_server.py, which executes it against the real repo and returns an observation.
  5. Append & loop — truncate the observation, append it as the next user turn, record per-step metrics, and repeat until finish or max_steps.
What runs where — the WASM/host split that CodeACT avoids
Inside the inferlet (WASM)On the host (tool_server.py)

Why the split exists: OpenHands' real tools need a host shell + Python env + the repo checkout, so they cannot run inside a WASM inferlet. Unlike CodeACT — whose tool is Boa-JS eval and does run in WASM — Pattern A must proxy tools over HTTP to the host. That means it keeps the paper's live-KV / no-re-prefill benefit but not the co-location / no-round-trip benefit (and on localhost the round-trip is ≈ 0 anyway).

Two more capabilities sit on the same structure. Robustness guards catch truncated JSON, degenerate "symbol-soup" output, and stuck read↔edit / repeated-bash cycles, nudging or force-finishing rather than looping forever. And a test-time-scaling fork (num_branches / branch_at_step) runs a shared trunk to step k, then forks both the live KV context and the tool-server workspace into N candidate trajectories that share steps 1…k — a branch operation a stateless client cannot express cleanly.

Shared prefix ~10k tokens, fork into N children, conc=1, decode 64/child. Pie B2 (single-call fork) vs vLLM two-phase + APC, matched prefixes.

4.5 · Memory-pressure / overcommit

Both engines share the same 244,704-token cache. At conc that barely fits, vLLM is slightly faster; at 1.9× overcommit, Pie OOM-crashes (no CPU-swap backstop on the vLLM driver) while vLLM degrades gracefully via APC evict + recompute. The "atomic fork + offload beats APC" thesis does not hold — Pie hits the wall at the same working-set size and crashes before it can exploit APC's weakness.

5Where the paper's agentic win comes from

The paper's ReACT / CodeACT / Swarm inferlets share one structure (ReACT shown):

let mut ctx = Context::new(&model)?;              // ONE context, created ONCE
ctx.system(SYSTEM_PROMPT); ctx.user("Question: …"); ctx.cue();
for step in 1..=max_steps {                       // 8 (ReACT/CodeACT), 32 (Swarm)
    let raw = ctx.generate(…).await?;             // decode action — appends to SAME ctx
    let observation = match tool {
        "Calculator" => calculator(arg),          // ← TOOL RUNS IN-PROCESS
        …
    };
    ctx.user("Observation: {observation}…"); ctx.cue(); // append to SAME live ctx
}

The loop lives inside the server, the tool runs in-process between steps. Versus a Python-client baseline, Pie eliminates three per-interaction costs — but only in the paper's setup; all vanish in ours:

Win conditionPaperOur runs
Model1B/3B (gen ≈ few ms → RTT is a big fraction)30B (gen dominates)
Clientremote, campus network (real RTT)localhost (RTT ≈ 0)
# I/Os8 / 8 / 32 (win scales)fewer, diluted by long gens
Concurrencyup to 128 agents → APC evictsfits → APC never evicts
Tool locationin-WASM (Rust fn, Boa JS)bash/edits → must be on host

6Where a real Pie win could still live

None is single-GPU-localhost-wallclock:

  • A genuine network gap between workers and the server → vLLM pays re-transmit + round-trip that Pie's server-side session avoids. The paper's dominant small-model mechanism; does not trigger Pie's OOM.
  • Mask-condense (structural, APC-impossible) → at condensation points the summarizing baseline emits new text → APC miss → re-prefill; Pie drops the stale middle and keeps the rest valid. A re-prefill-avoidance + capability win (not a decode speedup) — and, per §4.4b, only pays off under pressure.
  • Effective-KV > GPU with working offload → the only regime where fork + restore structurally beats APC-evict-recompute; blocked on the native-driver swap path.
  • Fix decode batching across forks → turns the fan-out loss into a tie, not a win.

7Conclusions

  • Pie's KV-reuse mechanisms are real and large (94.8 % prefill saved in OpenHands; 668k tokens in fan-out; organic cross-worker reuse; 99.7 % on fork delegation). They are not wallclock wins because vLLM APC captures the same reuse for free when it fits.
  • On a single local GPU, Pie's best case is a tie (N=1 fan-out + decode-parity). Every tie-breaker is either blocked by a Pie engine gap (serial fork-decode; OOM under pressure; per-call session overhead) or matched by APC.
  • Architecture matters a lot. The stateless coder-session was 3.65× slower; the loop-in-inferlet agent recovered most of that (3.1× faster), landing 1.18× off the baseline — so the huge deficit was mostly self-inflicted, not fundamental. But even the good architecture only approaches parity on localhost.
  • The paper's agentic win is genuine but conditional — small model, real network, many I/Os, concurrency, in-WASM tools — and our Python/bash-tool workloads on localhost with a big model satisfy none of them.
  • The honest, defensible contribution is deterministic prefill/token elimination + programmability (strategies APC cannot express), which matters for compute / energy / cost — not a wallclock win, unless one of the §6 conditions is built.
