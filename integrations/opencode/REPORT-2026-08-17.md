# pie vs mlx-lm vs vLLM-metal — results and provenance

**2026-08-17 · Qwen3-Coder-30B-A3B-4bit · Apple M5 Pro 48 GB · stock opencode**

Two questions, measured separately because a single wall-clock number cannot
answer either: **does the agent solve the task**, and **how fast**. Part 1 is the
results. Part 2 is the file map — which artifact produced which number, so any
figure here can be recomputed or challenged without a rerun.

**All three engines serve the identical weights.** pie's artifact is
`mlx-community/Qwen3-Coder-30B-A3B-Instruct-4bit` repacked into its container
format, not a separate conversion — 17.21 GB against the source's 17.20 GB,
`pie model info` names that repo as the source, and `--quant` (which would
requantize) was not used. Verified byte-level: 512-byte slices from the
midpoints of a 4-bit packed weight, its bf16 scales, and the 8-bit router all
appear **verbatim** in the artifact, and MLX's per-tensor override of `mlp.gate`
to 8 bits at group 64 carries through — pie's driver reports it at boot. So
every difference below is kernels, scheduling and serving strategy, with the
weights held constant.

# Part 1 — Results

## 1.1 The headline, and the number that outranks it

Thirty SWE-bench Verified instances, graded by
`swebench.harness.run_evaluation` in Docker. Every engine restarted its server
per instance; every model call went through one proxy on one clock.

| | pie | mlx-lm | vLLM-metal |
|---|---:|---:|---:|
| **SWE-bench resolved** | **5/30** | 4/30 | 4/30 |
| Sustained decode, token-weighted | **42.0 tok/s** | 35.3 | 17.0 |
| Agent calls per instance | **12.3** | 23.7 | 22.9 |
| Median call | **2.65 s** | 4.14 s | 6.64 s |
| p90 time to first token | 13.1 s | **4.2 s** | 6.9 s |
| Wall clock, 30 instances | **1h 25m** | 1h 33m | 3h 38m |
| Degenerate loops | 33% | 37% | 43% |

**Accuracy is parity.** One instance of spread over n=30; a two-instance swing
reorders it, and instances are demonstrably coin-flips on repeat runs.

**But every resolved instance came from the original ten.**

| engine | overall | original 10 | the 20 new |
|---|---:|---:|---:|
| pie | 5/30 | 5/10 | **0/20** |
| mlx-lm | 4/30 | 4/10 | **0/20** |
| vLLM-metal | 4/30 | 4/10 | **0/20** |

The first ten are django-only and were inherited from a run that had selected
them for solvability. The twenty added here span eleven other repositories and
**no engine resolved one of them**. So the headline describes a biased subset;
the unbiased half says this model-and-agent pairing resolves approximately none
of SWE-bench Verified. Sample at random next time and expect low single digits.

## 1.2 Throughput: pie's clearest win, and it is not the tok/s

pie sustains **1.19× mlx-lm and 2.47× vLLM-metal**, but the larger effect is
turn count: **pie needs half the agent round-trips** for the same work.

Agent wall clock is `turns × (prefill + decode)`. mlx-lm finishes within eight
minutes of pie while making **1.9× as many calls** — so an engine can lose wall
clock by provoking more turns without being slower per call. No instance-level
timing can separate those; that separation is the reason the proxy exists.

Throughput is **token-weighted** — `sum(completion_tokens)/sum(decode_s)` —
because a per-call rate on agentic traffic is dominated by two-token tool
replies and reaches four figures on a model whose bandwidth caps near 172 tok/s.
Zero calls across 1,770 had degraded usage records, so every token count is the
server's own rather than estimated.

## 1.3 Latency: pie wins the median, loses the tail

| engine | TTFT med | TTFT p90 | TTFT max | call med | call p90 | prompt med |
|---|---:|---:|---:|---:|---:|---:|
| pie | 0.97 | **13.12** | 57.88 | **2.65** | 22.31 | 11,433 |
| mlx-lm | 0.86 | **4.21** | 31.19 | 4.14 | **7.20** | 27,415 |
| vLLM-metal | **0.68** | 6.91 | 114.97 | 6.64 | 24.29 | 23,248 |

pie's p90 TTFT is 3.1× mlx-lm's, matching the controlled fixed-prompt result:
pie leads decode to 16k context and falls to **0.78×** at 28k.

**These columns are not controlled.** The engines took different trajectories
and so saw different prompt lengths — pie's median prompt is 11.4k tokens
against mlx-lm's 27.4k. For a controlled comparison see §1.4.

## 1.4 Fixed-prompt decode, interleaved (the controlled measurement)

Three rounds, order alternating each round, so thermal drift lands in both arms:

| prompt | pie | mlx-lm | ratio |
|---:|---:|---:|---|
| 5,840 | 67.6 | 66.2 | **1.02×** |
| 16,090 | 49.5 | 47.6 | **1.04×** |
| 28,390 | 28.1 | 35.8 | **0.78×** |

Per-engine spread was **0.2%**. Block-scheduled rather than interleaved, the
same comparison wobbled **21%** — enough to support either conclusion.

## 1.5 Engine work that landed

- **Neural-accelerator kernels.** M5's second matrix unit measures 31–32 TFLOP/s
  against 5.2 for the simdgroup unit. Attention, the routed MoE GEMM and the
  dense projections moved onto it: **TTFT at 28k went 57.3 s → 13.8 s (4.2×)**.
- **A cached Metal device handle.** `MTLCreateSystemDefaultDevice()` is not a
  getter — it costs 0.13–0.17 ms, ~50× the buffer allocation it serves, and ran
  twice per channel × ten channels **per token**. Caching it took channel
  registration from **2.70 ms to 0.04 ms** and a decode step from **17.43 → 14.17
  ms (1.23×)**, with generated text byte-identical across the two binaries.

## 1.6 Degeneration: the model's, not any engine's

All three engines loop on roughly a third of instances — pie 33%, mlx-lm 37%,
vLLM 43%, worst cases 140–263 repetitions of one line. Three independent
implementations landing in one band settles the attribution: this is the
checkpoint's behaviour under greedy decoding.

**A loop makes a run faster**, because it reaches the token cap sooner. Every
throughput and latency column above would score one as a win; only
`transcript_health.py` distinguishes them.

## 1.7 Determinism

- **Value layer, first measurement ever taken on Metal**: six runs × 32 steps,
  **32/32 bit-identical** on both per-token logprob and whole-vocab entropy.
  Previously unobservable — the serving path hardcodes `"logprobs": null`.
- **Greedy text** is byte-identical across boots and across binaries, out to
  1000-token generations.
- **But prefill chunk width changes the logits**: nine widths, eight distinct
  results, identical kernel selection throughout. The cause is reduction order,
  inherent to chunked attention over a paged cache.

## 1.8 Retractions from earlier work

| claim | status |
|---|---|
| pie 4/5 vs vLLM 1/5 on SWE-bench | **Retracted.** Asymmetric — pie got per-instance restarts, vLLM did not. Symmetric: pie 3/5, vLLM 4/5. |
| pie's loop rate is 5% | **Retracted.** That sampled four instances, three low-rate. At n=30 it is 33%. |
| Speculation causes the looping | **Retracted.** The bisect's own control produced a clean patch on the failing instance; spec-off loops too. |
| An accuracy regression in pie | **Retracted.** mlx-lm loops at the same rate on different instances. |

## 1.9 Measurement defects worth carrying forward

1. **A degenerate loop reads as a speed win** in every timing instrument here.
2. **The fire probe measured a kernel the server never runs** — a rows=1 decode
   takes split-K, but the server speculates and its verify fires take
   head-sharing. An A/B reporting "1.003×, no effect" had both arms on identical
   code.
3. **Speculation is not output-equivalent.** Kernel selection keys on row count,
   so a verify fire computes tokens with different arithmetic than the
   sequential decode it is assumed to match.
4. **A single agentic run cannot price anything.** opencode's own prompt varies
   run to run; instances flip between resolved and looping on repeat.

# Part 2 — Which file produced which number

## 2.1 Run the whole thing

```sh
# 1. generation — three arms, symmetric restarts, all calls proxied  (~6 h)
integrations/opencode/tools/swe30_three_way.sh

# 2. grading — Docker; needs colima's bundled lima on PATH
export PATH=$HOME/.local/lima/bin:$PATH
SWE_OUT=/tmp/swe30 SWE_RUN_TAG=swe30 integrations/opencode/tools/swe_grade_overnight.sh

# 3. the combined table
integrations/opencode/tools/swe30_report.py /tmp/swe30 --run-tag swe30
```

## 2.3 The instruments

**Harnesses**

| file | what it does |
|---|---|
| `tools/swe30_three_way.sh` | the 30-instance three-way; boots each engine, proxies every call, restarts per instance |
| `tools/swe_grade_overnight.sh` | waits for generation, then grades every arm in Docker |
| `tools/pie_mlx_interleaved.sh` | fixed-prompt decode, arms alternating per round to defeat thermal drift |
| `tools/four_way.sh` | pie / pie-original / mlx-lm / vLLM, with a repeat-first-arm drift control |
| `tools/loop_rate.sh` | repeats one configuration to measure how often it degenerates |
| `run_swebench.py` | drives one opencode run per instance; owns `--restart-cmd` |

**Analysis**

| file | what it computes |
|---|---|
| `tools/swe30_report.py` | the combined table; refuses to rank engines within two instances |
| `tools/call_stats.py` | token-weighted throughput and per-call latency percentiles |
| `tools/transcript_health.py` | `maxrep` — degeneration, engine-neutral, runs over any arm |
| `tools/turnlog.py` | the proxy: TTFT, decode wall, server-reported token counts |

**Guards** — each exists because its absence cost a measurement

| file | the failure it prevents |
|---|---|
| `tools/wait_for_memory.sh` | boots into insufficient memory. Fixed sleeps of 8 s and 30 s killed runs at instances 3 and 14 |
| `tools/require_quiet_gpu.sh` | starting an arm on a machine that cannot hold it |
| `tools/boot_pie.sh` | measuring a server this run did not start — `pkill -f "pie serve"` never matched the real argv |

**Probes (inferlets)**

| file | question |
|---|---|
| `runtime/engine/tests/inferlets/logprob-determinism/` | is decode deterministic at the value layer? |
| `runtime/engine/tests/inferlets/chunk-width-determinism/` | does prefill chunk width change the logits? |
| `runtime/engine/tests/inferlets/decode-rows-probe/` | per-fire decode cost by row count and context |

## 2.4 Raw data (committed)

`integrations/opencode/data-swe30/` — 676 KB, enough to recompute every table
without rerunning anything:

- `preds-<arm>.jsonl` — predictions fed to the grader
- `preds-<arm>.cases.jsonl` — per-instance state, seconds, patch bytes
- `calls-<arm>.jsonl` — every model call: TTFT, decode wall, token counts
- `<arm>.swe30_<arm>.json` — the graded reports, with `resolved_ids`
- `run.log`, `grade.log` — generation and grading transcripts

Not committed: `/tmp/swe30/wd-<arm>/` agent transcripts (~100 MB). Loop rates
were computed from them and are recorded here; regenerating requires a rerun.
